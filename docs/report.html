PHASE 1 – REQUIREMENT ANALYSIS & ERD DESIGN

PLAYGRID — Sports Tournament Management System

1. Introduction / System Description

Futsal and amateur sports tournaments across Pakistan are expanding rapidly, engaging hundreds of clubs, student athletes, and weekly fixtures. Traditionally, tournament organizers have relied on manual pen-and-paper brackets, uncoordinated messaging groups, and isolated spreadsheets to track team registrations, match scores, player stats, and league tables. This manual approach is slow, lacks transparent auditing, and is highly prone to calculation errors, missing match events, scheduling conflicts, and delayed results.

The purpose of the PLAYGRID Sports Tournament Management System is to provide an end-to-end, digital, 3NF-normalized relational database management system. PLAYGRID maintains comprehensive records of sports facilities, registered clubs, verified players, referee appointments, live match events (goals, cards, fouls), automated round-robin and knockout standings, and secure player registration fee tracking via local payment channels (JazzCash, EasyPaisa, Bank Transfer). Overall, the goal of this system is to eliminate manual calculation errors, provide instant public leaderboards, reduce paperwork, and enforce role-based access control.

2. Requirement Analysis

Requirement analysis was carried out to understand the real-world operational workflows of futsal tournaments in major Pakistani cities (Karachi, Lahore, Islamabad) and specify database requirements for transactional consistency, referential integrity, and fast querying.

2.1 Functional Requirements

The system must be able to:

  • Store and manage sporting venues with surface types (artificial turf, indoor wooden), spectator capacity, and floodlight availability.
  • Maintain tournament definitions with formats (League, Knockout), registration deadlines, prize pools, squad limits, and points rules (3 for Win, 1 for Draw, 0 for Loss).
  • Register clubs with logos, home cities, and club manager owner accounts.
  • Manage player bio details, CNIC verification, dates of birth, kit numbers, and field positions.
  • Track tournament team registrations, approval statuses, and fee payment receipts.
  • Schedule match fixtures with rounds, grounds, kickoff times, and appointed referees.
  • Record granular in-game match events including goals, yellow cards, and red cards with minute stamps.
  • Automatically calculate and rank tournament league standings (Played, Won, Drawn, Lost, GF, GA, GD, Points).
  • Track individual player awards for Top Goal Scorers (Golden Boot) and disciplinary fair play records.
  • Maintain a tamper-evident audit log of administrative actions.
2.2 Non-Functional Requirements

The system should:

  • Ensure referential integrity using primary keys, foreign keys, and check constraints.
  • Avoid duplicate records and maintain Third Normal Form (3NF) consistency.
  • Provide sub-second query response times for standings tables and match scoreboards.
  • Maintain data security and restrict unauthorized access through role-based access control.
  • Be scalable to accommodate multiple concurrent tournaments across multiple cities.

3. Identified Entities

After analyzing the requirements of PLAYGRID, the following 10 primary entities were identified:

  1. City — Administrative host cities and provinces
  2. Venue — Physical grounds, turf types, and facilities
  3. User — System users across roles (Admin, Organizer, Team Manager, Viewer)
  4. Tournament — Championship events, rules, entry fees, and prize pools
  5. Team — Registered futsal and sports clubs
  6. Player — Athletes, CNICs, positions, and bio data
  7. Registration — Tournament participation applications and statuses
  8. Payment — Registration fee payments, gateways, and receipts
  9. Referee — Match officials and licensing tiers
  10. Match — Scheduled fixtures, rounds, grounds, and match scores
  11. Match_Event — In-game occurrences (goals, cards, fouls) with minute stamps
  12. Standing — League standings, goal difference, and point tallies

These entities cover all major activities performed in sports tournament management.

7. Normalization (Applied)

The database is normalized up to Third Normal Form (3NF) by applying the following steps:

First Normal Form (1NF) – Applied
  • Removed multi-valued attributes and repeating groups.
  • Ensured each column stores single (atomic) values.
  • Created separate atomic rows for each in-game match event instead of comma-separated player strings.

Application: A separate table match_events is created. Each row contains MatchID, PlayerID, EventType, and Minute. Multiple goals or bookings in a match are not stored in one column, but as separate atomic records.

Second Normal Form (2NF) – Applied
  • Removed partial functional dependencies.
  • Ensured all non-key attributes depend on the complete primary key.

Application: The relationship between tournaments and teams is resolved using surrogate keys. Rather than placing payment transactions onto a composite (TournamentID, TeamID) key, a dedicated payments table was created with PaymentID as primary key and RegistrationID as a foreign key, ensuring payment amounts and transaction references depend fully on the primary key.

Third Normal Form (3NF) – Applied
  • Removed transitive dependencies ($X \to Y \to Z$).
  • Ensured non-key attributes depend only on the primary key.

Application: City names and provincial jurisdictions are extracted into a separate cities table. venues, teams, and tournaments store only CityID (FK). Geographic attributes are not repeated inside venue or tournament tables, completely preventing update anomalies.

Final Applied Tables Structure (Simplified)

After applying normalization up to 3NF, the final database structure consists of the following tables:

  • cities (CityID, Name, Province)
  • venues (VenueID, Name, Address, CityID FK, SurfaceType, Capacity, HasFloodlights)
  • users (UserID, Name, Email, PasswordHash, Role, Phone)
  • tournaments (TournamentID, Name, Format, Status, StartDate, EndDate, EntryFeePKR, PrizePoolPKR, CityID FK, OrganizerID FK)
  • teams (TeamID, Name, ShortName, CityID FK, ManagerID FK, FoundedYear)
  • players (PlayerID, FullName, CNIC, DateOfBirth, PreferredPosition, TeamID FK, KitNumber)
  • registrations (RegistrationID, TournamentID FK, TeamID FK, Status, RegisteredAt)
  • payments (PaymentID, RegistrationID FK, AmountPKR, PaymentMethod, TransactionRef, Status)
  • referees (RefereeID, FullName, CertificationLevel, CityID FK, Phone)
  • matches (MatchID, TournamentID FK, RoundNumber, HomeTeamID FK, AwayTeamID FK, VenueID FK, RefereeID FK, ScheduledAt, HomeScore, AwayScore, Status)
  • match_events (EventID, MatchID FK, TeamID FK, PlayerID FK, EventType, Minute)
  • standings (StandingID, TournamentID FK, TeamID FK, Played, Won, Drawn, Lost, GoalsFor, GoalsAgainst, GoalDifference, Points)

PHASE 2 — SQL IMPLEMENTATION

PLAYGRID — Sports Tournament Management System

SQL script:

CREATE DATABASE PlaygridDB;
USE PlaygridDB;

/* =========================================
   TABLE CREATION (DDL)
========================================= */
CREATE TABLE cities(
  CityID INT PRIMARY KEY,
  Name VARCHAR(50) NOT NULL UNIQUE,
  Province VARCHAR(50) NOT NULL
);

CREATE TABLE venues(
  VenueID INT PRIMARY KEY,
  Name VARCHAR(100) NOT NULL,
  Address VARCHAR(150) NOT NULL,
  CityID INT,
  SurfaceType VARCHAR(30) NOT NULL,
  Capacity INT NOT NULL,
  HasFloodlights BOOLEAN NOT NULL DEFAULT TRUE,
  FOREIGN KEY (CityID) REFERENCES cities(CityID)
);

CREATE TABLE users(
  UserID INT PRIMARY KEY,
  Name VARCHAR(100) NOT NULL,
  Email VARCHAR(150) NOT NULL UNIQUE,
  PasswordHash VARCHAR(255) NOT NULL,
  Role VARCHAR(30) NOT NULL,
  Phone VARCHAR(20)
);

CREATE TABLE tournaments(
  TournamentID INT PRIMARY KEY,
  Name VARCHAR(150) NOT NULL,
  Format VARCHAR(30) NOT NULL,
  Status VARCHAR(30) NOT NULL,
  StartDate DATE NOT NULL,
  EndDate DATE NOT NULL,
  EntryFeePKR DECIMAL(10,2) NOT NULL,
  PrizePoolPKR DECIMAL(10,2) NOT NULL,
  CityID INT,
  OrganizerID INT,
  FOREIGN KEY (CityID) REFERENCES cities(CityID),
  FOREIGN KEY (OrganizerID) REFERENCES users(UserID)
);

CREATE TABLE teams(
  TeamID INT PRIMARY KEY,
  Name VARCHAR(100) NOT NULL UNIQUE,
  ShortName VARCHAR(5) NOT NULL,
  CityID INT,
  ManagerID INT,
  FoundedYear INT,
  FOREIGN KEY (CityID) REFERENCES cities(CityID),
  FOREIGN KEY (ManagerID) REFERENCES users(UserID)
);

CREATE TABLE players(
  PlayerID INT PRIMARY KEY,
  FullName VARCHAR(100) NOT NULL,
  CNIC VARCHAR(20) UNIQUE,
  DateOfBirth DATE NOT NULL,
  PreferredPosition VARCHAR(30) NOT NULL,
  TeamID INT,
  FOREIGN KEY (TeamID) REFERENCES teams(TeamID)
);

CREATE TABLE registrations(
  RegistrationID INT PRIMARY KEY,
  TournamentID INT,
  TeamID INT,
  Status VARCHAR(30) NOT NULL,
  RegisteredAt TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (TournamentID) REFERENCES tournaments(TournamentID),
  FOREIGN KEY (TeamID) REFERENCES teams(TeamID)
);

CREATE TABLE payments(
  PaymentID INT PRIMARY KEY,
  RegistrationID INT,
  AmountPKR DECIMAL(10,2) NOT NULL,
  PaymentMethod VARCHAR(30) NOT NULL,
  TransactionRef VARCHAR(100) NOT NULL,
  Status VARCHAR(30) NOT NULL,
  FOREIGN KEY (RegistrationID) REFERENCES registrations(RegistrationID)
);

CREATE TABLE referees(
  RefereeID INT PRIMARY KEY,
  FullName VARCHAR(100) NOT NULL,
  CertificationLevel VARCHAR(30) NOT NULL,
  CityID INT,
  Phone VARCHAR(20),
  FOREIGN KEY (CityID) REFERENCES cities(CityID)
);

CREATE TABLE matches(
  MatchID INT PRIMARY KEY,
  TournamentID INT,
  RoundNumber INT NOT NULL,
  HomeTeamID INT,
  AwayTeamID INT,
  VenueID INT,
  RefereeID INT,
  ScheduledAt TIMESTAMP NOT NULL,
  HomeScore INT NOT NULL DEFAULT 0,
  AwayScore INT NOT NULL DEFAULT 0,
  Status VARCHAR(30) NOT NULL,
  FOREIGN KEY (TournamentID) REFERENCES tournaments(TournamentID),
  FOREIGN KEY (HomeTeamID) REFERENCES teams(TeamID),
  FOREIGN KEY (AwayTeamID) REFERENCES teams(TeamID),
  FOREIGN KEY (VenueID) REFERENCES venues(VenueID),
  FOREIGN KEY (RefereeID) REFERENCES referees(RefereeID)
);

CREATE TABLE match_events(
  EventID INT PRIMARY KEY,
  MatchID INT,
  TeamID INT,
  PlayerID INT,
  EventType VARCHAR(30) NOT NULL,
  Minute INT NOT NULL,
  FOREIGN KEY (MatchID) REFERENCES matches(MatchID),
  FOREIGN KEY (TeamID) REFERENCES teams(TeamID),
  FOREIGN KEY (PlayerID) REFERENCES players(PlayerID)
);

CREATE TABLE standings(
  StandingID INT PRIMARY KEY,
  TournamentID INT,
  TeamID INT,
  Played INT NOT NULL DEFAULT 0,
  Won INT NOT NULL DEFAULT 0,
  Drawn INT NOT NULL DEFAULT 0,
  Lost INT NOT NULL DEFAULT 0,
  GoalsFor INT NOT NULL DEFAULT 0,
  GoalsAgainst INT NOT NULL DEFAULT 0,
  GoalDifference INT NOT NULL DEFAULT 0,
  Points INT NOT NULL DEFAULT 0,
  FOREIGN KEY (TournamentID) REFERENCES tournaments(TournamentID),
  FOREIGN KEY (TeamID) REFERENCES teams(TeamID)
);

ALTER TABLE players ADD KitNumber INT DEFAULT 10;

PHASE 3 – DATABASE SECURITY (DCL)

PLAYGRID — Sports Tournament Management System

Database security is implemented to protect the PLAYGRID Tournament Management System from unauthorized tampering and score adjustments. Two dedicated non-root users are created with different access levels. The administrator is granted full permissions across all tables, while the team manager user is given limited read and registration permissions. One privilege is explicitly revoked to demonstrate role-based access control (RBAC) and database security.

SQL Script:

USE PlaygridDB;

/* Create Users */
CREATE USER 'playgrid_admin'@'localhost' IDENTIFIED BY 'admin123';
CREATE USER 'team_manager'@'localhost' IDENTIFIED BY 'manager123';

/* Grant Privileges */
GRANT SELECT, INSERT, UPDATE, DELETE
ON PlaygridDB.*
TO 'playgrid_admin'@'localhost';

GRANT SELECT
ON PlaygridDB.*
TO 'team_manager'@'localhost';

GRANT INSERT
ON PlaygridDB.players
TO 'team_manager'@'localhost';

FLUSH PRIVILEGES;

/* Revoke Privilege */
REVOKE INSERT
ON PlaygridDB.players
FROM 'team_manager'@'localhost';

FLUSH PRIVILEGES;

/* Successful Operations (Executed as playgrid_admin) */
SELECT * FROM tournaments WHERE TournamentID = 1;

INSERT INTO players VALUES

UPDATE venues SET Capacity = 650 WHERE VenueID = 1;

Security Explanation

Database security is important because it protects tournament records and financial prize money data from unauthorized access and misuse. In this system, different users are given different permissions according to their operational roles. The admin user can insert, update, delete, and view data, while the team manager user has limited access restricted to viewing schedules and registering team players. Revoking privileges prevents users from performing unauthorized actions such as creating fake tournaments, modifying match outcomes, or altering prize pool values. This improves data safety, privacy, and integrity in the PLAYGRID database.
